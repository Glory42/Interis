# "Movie" is the canonical term for a film, across both backend and frontend

The backend has always called this entity `Movie` (the `movies` table/module, `movieId` FK columns, `movie_interaction`). The frontend diverged: the feature directory is `features/films`, and the live public route is `/cinema/*` (itself a prior rename off an even older `/films/*`, which now survives only as a redirect stub). `CONTEXT.md` had flagged this split as unresolved since before this decision.

While planning a films/serials shared-component consolidation, we considered going the other direction — renaming the backend entity to `Cinema` to match the frontend's current route name — but rejected it. Renaming the backend would require a real migration (renaming the `movies` table, `movieId` FK columns referenced from `diary_entry`, `movie_interaction`, `lists`, `reviews`, `activity`, etc.), on top of a semantic mismatch: "Cinema" conventionally means a movie theater or the art form, not one individual film ("log this Cinema" reads wrong). "Movie" also matches TMDB's own API vocabulary, which the backend caches from directly, minimizing translation at that boundary.

We're instead unifying on `Movie` everywhere: `features/films` becomes `features/movies`, `/cinema/*` becomes `/movies/*` (matching the existing plural `/serials`), and `Cinema*`-prefixed components become `Movie*`-prefixed. Unlike the earlier `/films` → `/cinema` rename, no redirect is kept — `/cinema` and `/films` are removed outright rather than left as aliases, so any old bookmarks or shared links to them now 404.

The naming split turned out to run deeper than routes and components: `"cinema"` was also a string value persisted in the database (`list_entry.item_type`, `list.derived_type`), a CSS custom property (`--module-cinema`), and a field in the public, unauthenticated widget API (`GET /api/public/:username/top4` returned `key: "cinema"`). We unified all of it to `"movie"`, including a one-time data backfill migration (`drizzle/0051_backfill-cinema-to-movie-item-type.sql`) and accepting that the public API's `key` value changes too — a deliberate, explicit decision to prioritize one consistent name over preserving that field's stability for any external widget consumer, since there was no way to version or deprecate it gracefully from inside this refactor.
